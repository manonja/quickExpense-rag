## Executive Summary

Add a `transform` subcommand to the extract-rules CLI that converts YAML extraction output (ExtractedRule schema) to JSONL format (ParsedDocument schema) for database indexing. This bridges the extraction pipeline (TICKETS 1-6) with the RAG database builder.

**Key Principle**: Follow 80/20 approach - deliver core functionality without over-engineering.

---

## Design Decisions

### 1. CLI Structure
**Decision**: Rename existing `main` command → `extract` for clarity, add `transform` as peer command

**Rationale**:
- Creates explicit, scalable command structure
- `extract-rules extract` and `extract-rules transform` are clear, parallel actions
- Improves discoverability and user experience

### 2. Error Report Format
**Decision**: YAML only (no JSON support)

**Rationale**:
- Ticket specifies YAML
- Adding JSON would violate 80/20 principle and YAGNI
- Can add JSON later if genuine need arises

### 3. Logging Strategy
**Decision**: Reuse existing `RichHandler` setup from `extract` command

**Rationale**:
- Consistency in CLI output is important for UX
- `transform` is core part of same data pipeline
- Should share same look and feel

### 4. Test Coverage
**Decision**: Subprocess-based integration testing only (no unit tests for CLI)

**Rationale**:
- Integration tests provide highest value for MVP
- No need to unit test `typer`'s argument parsing
- Tests command as user would run it
- Validates argument wiring to transformer logic

### 5. Continue-on-Error Behavior
**Decision**: Exit code `1` if ANY errors occurred, even when `continue_on_error=True`

**Rationale**:
- Exit code `0` should signal complete, unqualified success
- Standard practice for tools in automated pipelines
- Allows scripts to detect partial failures
- Check `TransformationReport` and exit `1` if `report.skipped > 0` or `report.errors` is non-empty

### 6. Input Validation
**Decision**: CLI handles initial file existence check; transformer handles content validation

**Rationale**:
- Use `typer.Argument(exists=True)` for fast, user-friendly failure
- Follows existing pattern in `extract` command (cli.py:33)
- `YAMLTransformer` remains responsible for schema validation
- Clean separation of concerns

## Implementation Details

### Transform Command Signature

```python
@app.command()
def transform(
    input_yaml: Annotated[
        Path,
        typer.Argument(
            ...,
            help="Input YAML file from extract-rules",
            exists=True,
            file_okay=True,
            dir_okay=False,
        ),
    ],
    output_jsonl: Annotated[
        Path,
        typer.Argument(
            ...,
            help="Output JSONL file for IndexBuilder",
        ),
    ],
    continue_on_error: Annotated[
        bool,
        typer.Option(
            True,
            help="Skip errors and continue processing"
        ),
    ] = True,
    error_report: Annotated[
        Path | None,
        typer.Option(
            None,
            help="Path for error report YAML (optional)"
        ),
    ] = None,
    verbose: Annotated[
        bool,
        typer.Option(
            False,
            "--verbose",
            "-v",
            help="Enable verbose logging"
        ),
    ] = False,
) -> None:
    """
    Transform YAML extraction output to JSONL for database indexing.

    This command bridges the extraction pipeline (TICKETS 1-6) with the
    RAG database by converting ExtractedRule objects to ParsedDocument format.

    Example:
        uv run extract-rules transform output/rules.yml data/chunks.jsonl
    """
```

### Transform Command Logic Flow

```
1. Setup logging
   - verbose=True  → logging.DEBUG
   - verbose=False → logging.INFO
   - Use RichHandler for consistency

2. Instantiate transformer
   - transformer = YAMLTransformer()

3. Execute transformation
   - try:
       report = transformer.transform_yaml_to_jsonl(
           yaml_path=input_yaml,
           jsonl_path=output_jsonl,
           continue_on_error=continue_on_error
       )
   - catch CriticalTransformationError → print error, exit(1)
   - catch Exception → print unexpected error, exit(1)

4. Render summary report
   - Call _render_transform_report(report)
   - Show: total_rules, successful, skipped, errors
   - Display first 5 errors with "... and N more" if needed

5. Write error report (if requested)
   - if error_report and report.errors:
       with open(error_report, "w") as f:
           yaml.dump(report.model_dump(), f)
       console.print(f"📄 Error report: {error_report}")

6. Determine exit code
   - if report.errors or report.skipped > 0:
       raise typer.Exit(code=1)
   - else:
       raise typer.Exit(code=0)
```

### Report Renderer Implementation

```python
def _render_transform_report(report: TransformationReport) -> None:
    """Render rich-formatted transformation summary."""
    console.print()
    console.rule("[bold]Transformation Complete[/bold]")
    console.print()

    # Summary stats
    console.print(f"Total Rules:   [cyan]{report.total_rules}[/cyan]")
    console.print(f"Successful:    [green]{report.successful}[/green]")
    console.print(f"Skipped:       [yellow]{report.skipped}[/yellow]")
    console.print(f"Errors:        [red]{len(report.errors)}[/red]")
    console.print()

    # Error details (first 5)
    if report.errors:
        console.print("[yellow]⚠️  Errors Encountered:[/yellow]")
        for error in report.errors[:5]:
            console.print(f"  - {error['source_file']}: {error['error']}")
        if len(report.errors) > 5:
            console.print(f"  ... and {len(report.errors) - 5} more")
        console.print()

    # Output file
    console.print(f"Output: {report.output_file}")
    console.print()
```

## Edge Cases to Handle

### 1. File Permissions
**Issue**: Cannot write to output path or error report path

**Solution**:
```python
try:
    transformer.transform_yaml_to_jsonl(...)
except OSError as e:
    console.print(f"[red]Error: Cannot write to output path[/red]")
    console.print(f"[red]{e}[/red]")
    raise typer.Exit(code=1) from e
```

### 2. Empty Input
**Issue**: Valid YAML but contains no rules (`rules: []`)

**Solution**:
- Transformer handles gracefully
- CLI should report "0 total rules" and exit 0
- No error - this is valid (edge case but valid)

### 3. Partial Success
**Issue**: Some rules transform successfully, others fail

**Solution**:
- With `continue_on_error=True`: Generate JSONL with valid rules, exit 1
- Report shows: successful + skipped counts
- User can inspect error report to fix bad rules
